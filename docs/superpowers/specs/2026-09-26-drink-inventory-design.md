# ドリンク在庫管理システム 設計書

- 作成日: 2026-09-26
- ステータス: 設計承認済み

## 1. 目的

複数拠点（事務所・店舗）のドリンク在庫を一元管理する Web アプリ。スタッフが各自のスマホから、入荷・販売・拠点間移動・棚卸を入力し、誰がいつ何をしたかをすべて記録する。

## 2. 要件まとめ

| 項目 | 決定内容 |
|---|---|
| 利用形態 | 各スタッフが自分のスマホからアクセスする Web アプリ（A モード）。将来、共用端末モード（B モード）を端末単位で追加できる設計にする |
| ログイン | 名前を選択 + 4〜6 桁の PIN |
| 初期拠点 | 事務所、Kingyo、B-club、暖家、En（管理者が追加・名称変更・無効化可能） |
| 数量単位 | ケース + バラ。ドリンクごとに入数（1 ケースあたりの本数）を持つ。内部はすべてバラ本数 |
| 販売入力 | 任意の数量を任意のタイミングで入力（営業後まとめ入力も、1 本ずつ入力も可）。加えて棚卸で実数に補正 |
| 金額管理 | なし（数量のみ） |
| 拠点間移動 | 1 操作で完結。登録した瞬間に移動元が減り移動先が増える |
| 所属店舗 | スタッフごとに所属拠点を持つが操作制限はしない（ログイン直後の初期選択に使うだけ） |
| 取り消し | 本人は自分の入力を 24 時間以内なら取り消し可。それ以外（他人の入力・24 時間超）は管理者のみ。物理削除はしない |
| ドリンク登録 | 全員可能 |
| ドリンク廃止/復活 | 管理者のみ。廃止すると一覧・入力候補から非表示、過去の記録は残る |
| スタッフ登録 | 管理者のみ |
| 追加機能 | 全拠点在庫一覧、ドリンク名検索（どの拠点に何本あるか）、CSV 出力、ドリンク廃止 |

### 対象外（今回作らないもの）

金額管理、在庫が少ないときの警告、共用端末モード（B モード）、カテゴリ分け、「＋1」クイックボタン。いずれも後から追加しやすい構造にしておく。

## 3. 技術構成

- フロントエンド/サーバー: Next.js（App Router, TypeScript）
- データベース: Supabase（PostgreSQL）
- ホスティング: Vercel
- テスト: Vitest（ロジック）、ローカル Supabase（DB 関数）、Playwright（主要な画面の流れ）

選定理由: 5 拠点で同時に操作されても数量の整合性を保てる本物の RDB が必要で、無料枠で運用でき、Vercel とすでに連携しているため。

## 4. データ構造

### テーブル

**locations**（拠点）
- id, name（一意）, sort_order, is_active, created_at

**staff**（スタッフ）
- id, name, pin_hash（bcrypt）, role（`admin` | `staff`）, home_location_id → locations, is_active
- failed_pin_attempts, locked_until, created_at, updated_at
- 有効なスタッフの中で name は一意（部分ユニークインデックス）

**drinks**（ドリンク）
- id, name（一意）, units_per_case（1 以上の整数）, is_active, created_by → staff, created_at

**stock_movements**（在庫の動き。在庫の唯一の情報源であり、在庫操作のログを兼ねる）
- id, type（`receive` | `sale` | `transfer` | `adjust`）
- drink_id → drinks
- from_location_id → locations（null 可）, to_location_id → locations（null 可）
- quantity（整数。adjust 以外は 1 以上）
- counted_quantity（adjust のときだけ使う。実際に数えた本数）
- note, staff_id → staff, created_at
- batch_id（1 回の送信ごとにクライアントが作る UUID。まとめて入力したときのグループ ID であり、二重送信を防ぐ冪等キーも兼ねる）
- voided_at, voided_by → staff（取り消し情報。null なら有効）

type ごとの拠点の制約:

| type | from_location_id | to_location_id | 在庫への影響 |
|---|---|---|---|
| receive（入荷） | null | 必須 | to に +quantity |
| sale（販売） | 必須 | null | from から −quantity |
| transfer（移動） | 必須 | 必須（from と別の拠点） | from −quantity / to +quantity |
| adjust（棚卸調整） | null | 必須 | to に +quantity（quantity は差分なので負の値もあり） |

**audit_logs**（在庫以外の操作ログ）
- id, staff_id → staff, action（例: `staff.create`, `staff.update`, `staff.reset_pin`, `staff.unlock`, `drink.create`, `drink.deactivate`, `drink.activate`, `location.create`, `location.update`, `movement.void`, `login.locked`）
- target_type, target_id, details（jsonb）, created_at

### 在庫数の計算

- 在庫数は保存せず、取り消されていない `stock_movements` を拠点・ドリンクごとに集計して求める（ビュー `stock_levels`）
- 棚卸では、その時点の帳簿上の在庫を読み、`quantity = counted_quantity − 帳簿上の在庫` として adjust を登録する
- 表示するときだけ「x ケース + y 本（計 n 本）」に換算する。マイナス在庫は「計 −n 本」と表示する
- 在庫がマイナスになる操作は、画面で確認したうえで登録を許可する

### 整合性

- 在庫を変える処理（入荷・販売・移動・棚卸・取り消し）は PostgreSQL の関数として実装し、1 トランザクションで実行する
- まとめて入力したときは、全件成功か全件失敗のどちらかにする
- 在庫を変える関数はすべて、対象の（拠点, ドリンク）の組ごとにトランザクション単位のアドバイザリロック（`pg_advisory_xact_lock`）を取ってから処理する。これにより棚卸で帳簿上の在庫を読んでから差分を書くまでの間に、ほかの操作が割り込めない
- 二重送信を防ぐため、クライアントが送信ごとに `batch_id` を作って送る。同じ `batch_id` の記録がすでにあれば、何もせずに成功として返す

## 5. 画面構成

スマホ優先。画面下にタブを並べる。

1. **在庫**（ホーム）
   - 画面上部で拠点を切り替える（初期値は所属拠点。「全拠点」も選べる）
   - ドリンク名で検索できる（ひらがなとカタカナ、全角と半角の違いを区別しない）
   - 1 拠点を選んだとき: ドリンクごとの在庫一覧
   - 全拠点を選んだとき: ドリンク × 拠点の表（横スクロール）
   - ドリンクをタップすると、そのドリンクの最近の履歴を表示
2. **入力**
   - 入荷 / 販売 / 移動 / 棚卸をタブで切り替え
   - ドリンクを選ぶ（検索可）→ ケース数とバラ数を入れる → 確定
   - 複数のドリンクを 1 回でまとめて入力できる
   - 移動では移動元と移動先を選ぶ。棚卸では実際に数えた数を入れると、帳簿上の数との差を表示してから確定する
3. **履歴**
   - すべての操作を新しい順に表示。拠点・ドリンク・スタッフ・種類・期間で絞り込める
   - 取り消せる記録にだけ「取り消し」ボタンを出す。取り消し済みの記録は取り消し線と取り消した人を表示する
   - 表示中の条件で CSV 出力できる
4. **ドリンク**
   - 一覧と新規登録（全員可能）
   - 廃止・復活（管理者のみ）。廃止済みのドリンクは「廃止済みも表示」を選んだときだけ表示する
5. **管理**（管理者だけに表示）
   - スタッフ: 登録、編集（名前・権限・所属拠点）、PIN のリセット、ロック解除、無効化
   - 拠点: 追加、名前の変更、表示順の変更、無効化
   - 在庫一覧の CSV 出力
   - 操作ログ（audit_logs）の閲覧

**ログイン画面**: 有効なスタッフの名前一覧から選び、PIN を入力する。

CSV は Excel で文字化けしないよう、BOM 付きの UTF-8 で出力する。

## 6. 認証と権限

### ログイン

- Supabase Auth は使わず、PIN ログインを自前で実装する
- ブラウザからデータベースには直接アクセスしない。すべての読み書きは Next.js のサーバー側（Server Actions / Route Handlers）を通す。サーバーは Supabase の Postgres 接続文字列（`DATABASE_URL`、Transaction pooler）で直接接続し、接続情報はサーバーだけが持つ
- Supabase のすべてのテーブルで RLS を有効にし、anon と authenticated には何も許可しない（外部からの直接アクセスをすべて拒否する）
- ログインに成功したら、署名付き JWT を httpOnly・Secure・SameSite=Lax の Cookie に入れる（有効期限 30 日）
- サーバーは操作のたびに Cookie を検証し、DB からスタッフを読み直して、有効かどうかと権限を確認する（無効化されたスタッフは即座に使えなくなる）
- ログに記録する staff_id は、必ずサーバー側でセッションから決める。クライアントから送られた値は使わない

### PIN

- 4〜6 桁の数字。bcrypt で暗号化して保存する
- 5 回連続で間違えると 15 分ロックする。ログインに成功したら失敗回数を 0 に戻す。管理者はロックを解除できる
- ロックがかかったら audit_logs に記録する

### 権限

| 操作 | スタッフ | 管理者 |
|---|:---:|:---:|
| 在庫を見る、入荷/販売/移動/棚卸の入力 | ○ | ○ |
| ドリンクの登録 | ○ | ○ |
| 自分の入力を 24 時間以内に取り消す | ○ | ○ |
| 他人の入力や 24 時間を過ぎた入力の取り消し | × | ○ |
| ドリンクの廃止・復活 | × | ○ |
| スタッフ・拠点の管理 | × | ○ |

- 自分自身を無効化したり、管理者でなくしたりはできない（管理者が 0 人になるのを防ぐ）
- 最初の管理者はセットアップ用スクリプト（seed）で作る

### 将来の B モード（共用端末）への拡張

端末に「共用端末」のフラグを持たせ、その端末では操作のたびに名前と PIN を入力させる。ログイン・PIN の仕組みは A モードと同じものを使うので、DB の変更はほぼ必要ない。

## 7. エラー処理

- 入力チェックは画面とサーバーの両方で行う（zod のスキーマを共有する）
- 在庫を変える処理は DB 関数の中でトランザクションとして実行し、途中で失敗したらすべて元に戻す
- 通信エラーのときは入力内容を残し、同じ `request_id` で再送信できるようにする
- 取り消し済みの記録をもう一度取り消そうとしたとき、権限がないときは、わかりやすいエラーメッセージを返す

## 8. テスト

- **Vitest**: ケースとバラの換算、取り消しできるかの判定（本人かどうか・24 時間以内か・管理者か）、入力チェック、権限チェック
- **PGlite（Node 上で動く PostgreSQL。Docker 不要）**: マイグレーション、リポジトリ層、在庫を変える DB 関数（入荷・販売・移動・棚卸・取り消し）、在庫の集計、冪等キーの動作（PGlite は接続が1本なので、同時操作のロックはコードレビューで確認する）
- **Playwright**: ログイン → 入荷 → 移動 → 在庫確認 → 取り消し の流れ、スタッフには管理画面が表示されないこと（PIN のロックは PGlite のテストで確認する）。DB には pglite-socket で起動した PGlite を使う

## 9. 実装の順番

1. 土台づくり: Next.js と Supabase の準備、テーブル作成（マイグレーション）、seed（拠点 5 つ、最初の管理者）
2. PIN ログインとセッション
3. ドリンクの登録と在庫一覧（検索・全拠点表示つき）
4. 入荷 / 販売 / 移動 / 棚卸の入力
5. 履歴、取り消し、CSV 出力
6. 管理画面（スタッフ、拠点）
7. Vercel で公開

## 10. 追加仕様（v1.1）

- **入力画面の一括入力**: 入力画面は「ドリンクを1行ずつ選ぶ」形式をやめ、有効なドリンクをすべて表で表示する。各行にケース・本の入力欄と、選んでいる拠点（移動では移動元）の現在の帳簿在庫を表示する（棚卸では「数えた数 − 帳簿」の差も表示）。上部の「絞り込み」でドリンク名を絞り込める（絞り込んでも入力済みの値は消えない）。ケースか本のどちらかを入力した行だけを登録する。数量は数字のみ（`1e3` などは不可）、1行あたり 100000 本まで。入荷・販売・移動では合計 0 本の行はエラー、棚卸では 0 本も登録できる。入力した行が1つもないときは「ドリンクの数量を入力してください」と表示する。一度に登録できるのは 500 件まで（従来の 50 件から引き上げ）。登録後は数量とメモを空に戻し、「入荷 2件登録しました」のように種類と件数を表示する。
  - 入力済みの行が絞り込みで隠れているときは「入力中 N件（うち M件は絞り込みで非表示）」と「入力済みを表示」ボタンを出す。そのまま「登録する」を押すと、隠れているドリンク名を一覧で確認し、「非表示の分も含めて登録する」を押したときだけ（隠れている行も含めて）登録する。
  - 入力中の行があるときに種類（入荷/販売/移動/棚卸）を切り替えようとすると、「入力中のN件を消して「○○」に切り替えますか？」と確認し、「消して切り替える」を押したときだけ入力を消して切り替える。
  - 送信する各行には画面が使った「1ケースの本数」を含め、サーバーで現在の値と違えば（入力中に誰かがドリンクを編集した場合）何も登録せず「1ケースの本数が変更されました。画面を再読み込みしてください」と返す。
- **入力画面の初期値**: `/entry?drink=<ドリンクID>&location=<拠点ID>` で開くと、絞り込みにそのドリンク名が入り、拠点（移動元）がその拠点になる（どちらも省略可。無効な値は無視する）。
- **在庫画面からの移動**: 在庫画面のドリンク名を押すと、そのドリンクの入力画面を開く（拠点を1つ選んでいるときはその拠点も引き継ぐ）。履歴へは名前の横の「履歴」から移動できる。
- **ドリンクの編集**: ドリンク名と1ケースの本数は、ログインしているスタッフなら誰でも編集できる。変更したときは監査ログ（`drink.update`、変更前と変更後の名前・1ケースの本数）を残し、管理画面の操作ログには「コーラ → コーラ500、24本/ケース → 12本/ケース」のように変わった部分だけを表示する。何も変わっていないときは記録しない。在庫は本数で持っているので、1ケースの本数を変えても在庫の本数は変わらない（ケース表示だけが変わる）。廃止・復活は従来どおり管理者のみ。
- **自分のPIN変更**: ヘッダーの自分の名前から開く「アカウント」画面で、現在のPINを入力したうえで新しいPIN（4〜6桁、確認入力つき）に変更できる。現在のPINが違う、新しいPINが現在と同じ、確認が一致しない場合はエラー。現在のPINの誤りはログインと同じ回数に数え、5回続けて間違えると15分間ロックする（ロック中はログインも PIN 変更もできない。成功すると回数を0に戻す）。変更したときは監査ログ（`staff.change_pin`）を残す。対象は常にログイン中の本人のみ（管理者による他人のPINリセットは従来どおり）。
- **サービス名**: 「遊栄ドリンク在庫管理システム」に変更（ページタイトル、ヘッダー、ログイン画面）。

## 11. 原価・棚卸差異（v1.2）

在庫管理の画面・動作は変更しない。管理画面に「原価・棚卸差異」への入口を追加し、別ページで提供する。閲覧・設定はすべて**管理者のみ**。販売価格・売上・会計ソフト向け仕訳 CSV は対象外。

### 11.1 データ

- **drink_prices**: id, drink_id → drinks, unit_cost `numeric(12,2)`（1本あたり・税抜・円）, effective_from `date`（JST の日付）, created_by → staff, created_at。`unique (drink_id, effective_from)`。
  - ある日 d の卸価格 = effective_from ≤ d のうち最新の行。該当なしは「価格未設定」。
  - 入力はケース単価でも可（画面で ÷ 1ケースの本数 → 小数第2位で四捨五入して保存）。
  - 登録・削除は audit_logs に記録（`price.create`, `price.delete`）。更新は「同じ適用開始日で登録し直す」＝上書き（`price.update`）。
- **app_settings**: key text primary key, value jsonb, updated_by, updated_at。初期値: `tax_rate` = 10（%）、`variance_qty_threshold` = 5（本）、`variance_amount_threshold` = 3000（円）。変更は audit_logs（`settings.update`）。
- 既存テーブルと同様に RLS を有効にする。

### 11.2 計算（店舗 × 月、JST の暦月）

日付はすべて movement の created_at を JST に変換した日付で判定する。取り消し済みの movement は含めない（過去月の記録を後から取り消すと、その月の数字も変わる。画面に注記する）。

| 項目 | 定義 |
|---|---|
| 月初在庫本数 / 月末在庫本数 | 月初 00:00 JST 時点 / 翌月初 00:00 JST 時点までの movement の合計 |
| 月初在庫金額 | 月初本数 × 月初日の卸価格 |
| 月末在庫金額 | 月末本数 × 月末日の卸価格 |
| 仕入額 | Σ 入荷本数 × 入荷日の卸価格 |
| 移動入 / 移動出 | Σ 移動本数 × 移動日の卸価格（全店合計では相殺） |
| 棚卸差異金額 | Σ 棚卸の差異本数 × 棚卸日の卸価格（マイナス = ロス） |
| 売上原価 | 月初在庫金額 ＋ 仕入額 ＋ 移動入 − 移動出 − 月末在庫金額 |
| ロス率 | −棚卸差異金額 ÷ 売上原価（売上原価が 0 以下なら空欄） |

- 在庫評価は「その時点で有効な最新の卸価格」（最終仕入原価法に準じる）。
- 金額は行（ドリンク単位）ごとに 1 円未満を四捨五入してから合計する。消費税 = 税抜合計 × 税率（1 円未満切り捨て）、税込 = 税抜 + 消費税。
- 価格未設定のドリンクが関わる金額は計算に含めず、「価格未設定」件数と対象ドリンクを画面・CSV に明示する。

### 11.3 画面（/admin/costs 以下）

- **月次集計**: 期間（開始月〜終了月）と拠点で絞り込み。店舗 × 月の表（上記項目）＋全店合計。価格未設定の警告。
- **棚卸差異**: 棚卸ごとの明細（日時・拠点・数えた人・ドリンク・帳簿・実数・差異本数・差異金額）、店舗 × 月のロス集計、ドリンク別の差異ランキング。差異が「|本数| ≥ variance_qty_threshold または |金額| ≥ variance_amount_threshold」の行を強調。
- **卸価格**: ドリンクごとの現在の卸価格と履歴。追加（適用開始日・1本単価 or ケース単価）、削除。
- **設定**: 税率・差異の強調基準。
